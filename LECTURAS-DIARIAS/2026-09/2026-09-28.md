# Patrones de Diseño — Singleton, Factory, Observer

**Fecha:** 2026-09-28
**Categoría:** I — Ingeniería y Diseño
**Formato:** Manual técnico práctico

---

## 1. QUÉ ES

Un patrón de diseño es una **solución reutilizable y probada para un problema recurrente** en el diseño de software. No es código copiado: es una **plantilla conceptual** que resuelve una clase de problema específica, con sus reglas, sus ventajas y sus trampas. Los patrones no inventan nada nuevo; **formalizan lo que los buenos ingenieros ya hacen por instinto**, y les dan un nombre común para comunicarse.

Los tres patrones de esta lectura son de los más usados del catálogo clásico (el "Gang of Four", 1994) y cubren tres necesidades distintas:

- **Singleton** — *Creacional*: garantiza que exista **una sola instancia** de una clase en todo el programa, con un punto de acceso global.
- **Factory** — *Creacional*: **centraliza la creación de objetos**, para que el código cliente no dependa de clases concretas sino de una interfaz.
- **Observer** — *Comportamental*: define una relación **uno-a-muchos** donde un objeto notifica a otros cuando cambia su estado, sin acoplarlos entre sí.

Regla de oro: un patrón se usa **cuando resuelve un problema real**, nunca por moda ni por "verse profesional". Un patrón mal aplicado es más caro que no usar ninguno. La señal de que lo necesitas es **dolor repetido**: duplicación, acoplamiento, dificultad para testear o para extender.

## 2. CÓMO FUNCIONA

### Singleton — una sola instancia, un solo punto de acceso

El mecanismo es simple: el **constructor se hace privado** (nadie puede llamar `new` desde afuera) y se expone un **método estático** que devuelve la instancia única, creándola solo la primera vez.

```
class Config {
  static instancia = null;
  constructor() { /* privado */ }
  static get() {
    if (!this.instancia) this.instancia = new Config();
    return this.instancia;
  }
}
const a = Config.get();  // misma referencia
const b = Config.get();  // misma referencia
a === b  // true
```

**Por qué opera así:** garantiza estado consistente. Si dos partes del programa leen configuración, y cada una crea su propia copia, una puede leer un valor y la otra un valor distinto → bugs invisibles. Con Singleton, todos leen **el mismo objeto**.

**Ejemplo real:** una conexión a base de datos, un logger, un cache, la configuración global. Abrir 50 conexiones a la BD porque cada módulo crea la suya es un desastre de recursos; con Singleton abres una y la compartes.

**Trampa clásica:** el Singleton es un **global disfrazado**, y los globales dificultan los tests (no puedes inyectar un objeto falso fácilmente). Se usa con moderación; para configuración y conexiones puntuales está bien, para todo lo demás sospecha.

### Factory — separar la creación del uso

El mecanismo: en lugar de que el cliente haga `new ClaseConcreta()`, llamas a un **método factory** que decide qué objeto concreto devolver según un parámetro o contexto.

```
class AnimalFactory {
  static crear(tipo) {
    if (tipo === 'perro') return new Perro();
    if (tipo === 'gato') return new Gato();
    throw new Error('Tipo desconocido');
  }
}
// El cliente NO sabe qué clase concreta crea:
const mascota = AnimalFactory.crear('perro');
mascota.hablar();  // "Guau"
```

**Por qué opera así:** el código cliente queda **desacoplado** de las clases concretas. Si mañana agregas `Loro`, solo tocas la factory, no las 40 líneas que crean animales. Sin factory, cada punto de creación tendrías que editar un `if/else` → duplicación y riesgo de olvidar un caso.

**Ejemplo real:** cualquier sistema donde el tipo de objeto depende de datos de entrada — un parser que crea el handler según el formato del archivo (JSON, CSV, XML), un sistema de pagos que crea el procesador según el método (tarjeta, PayPal, transferencia), un juego que crea enemigos según el nivel.

**Trampa clásica:** no crees una factory "por si acaso". Si solo tienes una clase concreta y no ves que va a crecer, la factory añade una capa innecesaria. Factory se justifica cuando la **variedad es real y probable**.

### Observer — notificar sin acoplar

El mecanismo: hay un **sujeto** (observable) que mantiene una lista de **observadores** (suscriptores). Cuando el sujeto cambia de estado, recorre la lista y llama a un método de notificación en cada observador. Los observadores se suscriben y se desuscriben dinámicamente.

```
class Tienda {
  constructor() { this.suscriptores = []; }
  suscribir(obs) { this.suscriptores.push(obs); }
  notificar(msg) {
    this.suscriptores.forEach(o => o.actualizar(msg));
  }
}
class Cliente {
  actualizar(msg) { console.log('Recibí: ' + msg); }
}
```

**Por qué opera así:** el sujeto **no conoce** a los observadores concretos; solo sabe que implementan `actualizar()`. Así puedes agregar un nuevo tipo de observador sin tocar el sujeto. Es la base de los **eventos**: botones, listeners, pub/sub, notificaciones push.

**Ejemplo real:** una tienda online que notifica a los clientes cuando un producto vuelve a stock; un dashboard que se actualiza cuando cambia un precio; el sistema de eventos de cualquier UI ("click", "scroll"). En arquitectura de microservicios, el patrón pub/sub (eventos) es el mismo concepto a escala de servicios.

**Trampa clásica:** si un observador hace trabajo pesado o lanza error, puede frenar a todos los demás. Se mitiga con manejo de errores por observador y, a escala, con colas de mensajes asíncronas.

## 3. APLICACIÓN PRÁCTICA — 5 pasos para HOY

### Paso 1 — Audita tu código por duplicación de instancias
Abre tu proyecto y busca dónde se crean **múltiples copias** de lo mismo: conexiones, configuraciones, servicios. Si encuentras más de una, ese es tu candidato a Singleton. **Checklist:** ¿una sola instancia evitaría un bug o un desperdicio de recursos? ¿Sí? → aplica Singleton. ¿No? → no lo toques.

### Paso 2 — Detecta los `if/else` de creación repetidos
Busca en tu código los lugares donde eliges qué clase crear según un tipo. Si el mismo `if (tipo === 'x') return new X()` aparece en **2+ sitios**, extrae una Factory. **Ejercicio:** escribe la firma `factory.crear(tipo)` y mueve el switch ahí. Con eso, el siguiente cambio de tipos toca un solo archivo.

### Paso 3 — Convierte una notificación manual en Observer
¿Tienes código que, tras un cambio, llama directamente a 3 funciones para avisarles? (`actualizarPrecio(); actualizarDashboard(); enviarEmail();`) Eso es acoplamiento. Refactoriza a una lista de suscriptores: registra cada función como observador y notifica con un solo `notificar()`. **Checklist:** ¿agregar un nuevo "avisado" requiere tocar el código del que cambia? Si sí → aplica Observer.

### Paso 4 — Escribe un test que demuestre el desacople
Para el patrón que apliques, escribe **un test** que verifique el comportamiento clave: con Singleton, que `get()` devuelva siempre la misma referencia; con Factory, que `crear('perro')` devuelva un objeto que responda a `hablar()`; con Observer, que al notificar, todos los suscriptores reciban el mensaje. Un patrón sin test es una opinión, no una garantía.

### Paso 5 — Documenta el patrón en tu README o wiki
Escribe 3 líneas por patrón usado: **dónde está, qué problema resuelve, y cómo se agrega un caso nuevo** (nuevo tipo en Factory, nuevo suscriptor en Observer). Esto convierte el patrón en conocimiento del equipo y evita que alguien lo "refactorice" de vuelta al caos por no entenderlo.

## 4. EJEMPLO REAL — Sistema de notificaciones de una tienda e-commerce

Imagina una tienda online con 40.000 productos y un sistema de "avisarme cuando vuelva a stock". Sin patrones, el flujo de cada restock sería:

```
// ANTES — sin Observer: acoplado y frágil
function restockProducto(producto) {
  producto.stock = 100;
  enviarEmailClientes(producto);      // hardcodeado
  actualizarDashboard(producto);      // hardcodeado
  actualizarBusqueda(producto);       // hardcodeado
  // ...cada función nueva = editar aquí
}
```

Cada vez que agregas un canal (push, SMS, Slack del equipo), tienes que **editar** `restockProducto`. Un error en un canal rompe todo el restock. Con Observer:

```
// DESPUÉS — con Observer: extensible y aislado
const stockService = new StockService();          // sujeto
stockService.suscribir(new EmailNotifier());
stockService.suscribir(new DashboardUpdater());
stockService.suscribir(new SMSNotifier());        // nuevo canal: 1 línea

function restockProducto(producto) {
  producto.stock = 100;
  stockService.notificar(producto);               // avisa a todos
}
```

**Dato concreto:** en sistemas con eventos (patrón Observer/pub-sub), el costo de agregar un nuevo consumidor cae de **editar el emisor (riesgo de romper todo)** a **registrar un suscriptor (riesgo cero para el resto)**. En una arquitectura de microservicios con colas de mensajes, esto es lo que permite escalar de 3 a 30 servicios sin que cada cambio en un servicio rompa a los otros. El tiempo de integración de un nuevo consumidor baja típicamente de **días a horas**, y el riesgo de regresión se limita al nuevo suscriptor.

**Comparación antes/después:**
| Aspecto | Sin Observer | Con Observer |
|--------|-------------|--------------|
| Agregar canal nuevo | Editar el emisor (riesgo) | Registrar suscriptor (1 línea) |
| Un canal falla | Puede romper el emisor | Aislado, no afecta al resto |
| Testear | Difícil, acoplado | Fácil, inyectas suscriptores falsos |
| Escalar consumidores | Frágil | Natural (pub/sub, colas) |

## 5. RETO DEL DÍA — 5 a 10 minutos

Abre **el archivo más sucio de tu proyecto** (el que más cambias, el que más te da miedo tocar) y haz esto:

1. **Identifica un solo punto de dolor** de los tres patrones: ¿creas varias veces lo mismo? (Singleton) ¿tienes `if/else` de creación repetidos? (Factory) ¿llamas directamente a varios "avisados" tras un cambio? (Observer).
2. **Aplica el patrón mínimo** solo a ese punto: extrae la factory, centraliza la instancia, o convierte las llamadas directas en suscriptores.
3. **Corre el proyecto y verifica** que el comportamiento no cambió (debe ser idéntico, solo mejor estructurado).
4. **Escribe el test** del Paso 4 para ese patrón.

**Regla de salida:** si en 10 minutos no lo aplicaste, anota en una línea **qué patrón usarías y dónde**, y deja el archivo anotado con un comentario `// TODO: aplicar Factory aquí`. El objetivo del reto no es refactorizar todo: es **entrenar el ojo** para reconocer el patrón correcto en el momento correcto.
