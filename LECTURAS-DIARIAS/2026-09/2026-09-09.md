# Ley de los Contenedores (Docker)

## 1. QUÉ ES

Los contenedores Docker son unidades de ejecución aisladas que emulan un sistema operativo completo dentro de un kernel de Linux compartido. A diferencia de las máquinas virtuales, que emulan hardware completo y requieren un sistema operativo completo por contenedor, Docker utiliza namespaces y cgroups del kernel para aislar procesos, red, almacenamiento y recursos. Un contenedor combina la portabilidad de una imagen (código, dependencias y configuración) con la eficiencia de un sistema operativo ligero. La imagen es el plano de construcción (Dockerfile) que define el entorno; el contenedor es la instancia en ejecución. Esta arquitectura permite que aplicaciones se ejecuten consistentemente en cualquier entorno, desde un laboratorio de desarrollo hasta producción en vivo, reduciendo el problema de "funciona en mi máquina" a casi cero.

Un contenedor Docker puede compartir el kernel del host, lo que lo hace extremadamente rápido (segundos para iniciar) y consume menos memoria que una VM (generalmente 1-2 GB vs 5-20 GB). La aislamiento se logra mediante namespaces que proporcionan visibilidad independiente de procesos, redes, montajes de volumen y puntos de acceso. Esto significa que cada contenedor tiene su propia vista del sistema, sus conexiones de red y su sistema de archivos, incluso cuando coexisten múltiples contenedores en el mismo host.

## 2. CÓMO FUNCIONA

### Mecanismo Técnico

Docker funciona mediante tres capas principales: el motor de contenedores (containerd), el runtime de Docker (docker) y las imágenes preconstruidas. Cuando se crea una imagen con un Dockerfile, el motor construye una estructura de directorios que incluye el código, librerías, configuraciones y scripts necesarios. Durante la ejecución, el runtime crea un contenedor que monta volúmenes de datos persistentes (bind mounts o volumes) y configura interfaces de red específicas.

El kernel de Linux proporciona las primitivas necesarias: namespaces para aislamiento de procesos, red, dispositivos y cgroup para control de recursos. Docker también gestiona el ciclo de vida de los contenedores (create, start, stop, restart, remove) y el estado de los puertos, volúmenes y redes.

### Ejemplo Concreto

Consideremos una aplicación web Node.js que requiere MongoDB como base de datos. Sin Docker, instalar Node.js y MongoDB en cada máquina de desarrollo y producción implicaría inconsistencias. Con Docker:

1. **Imagen de base**: Se crea una imagen `node:18-alpine` que contiene Node.js 18 y dependencias mínimas.
2. **Imagen de aplicación**: Se construye una imagen que copia el código de la aplicación y las dependencias desde la imagen base.
3. **Contenedor**: Se ejecuta el contenedor con `docker run -d -p 3000:3000 --name mi-app mi-app-imagen`.
4. **Persistencia**: Se monta un volumen para el almacenamiento de datos: `docker run -v /data/mongo:/data/mongo mi-app-imagen`.

El resultado es que la aplicación corre en cualquier entorno con la misma configuración, y los datos persisten en el volumen en lugar de perderse al detener el contenedor.

### Comparación: Contenedores vs Máquinas Virtuales

| Característica | Contenedores (Docker) | Máquinas Virtuales (VM) |
|----------------|------------------------|--------------------------|
| Aislamiento | Namespaces + cgroups (kernel) | Hypervisor + OS completo |
| Tiempo de inicio | Segundos | Minutos a horas |
| Consumo de memoria | 1-2 GB | 5-20 GB |
| Complejidad de infraestructura | Simple (Docker Engine) | Alta (hypervisor, OS, networking) |
| Portabilidad | Imagen = unidad de despliegue | Disco completo con OS |
| Escalabilidad | Horizontal (orchestrators como Kubernetes) | Requiere VMware/Proxmox |

## 3. APLICACIÓN PRÁCTICA

### Paso 1: Elegir una imagen base estable
Selecciona una imagen oficial o construida internamente que coincida con las dependencias de tu proyecto. Para aplicaciones web, imágenes como `node:18-alpine`, `python:3.11-slim` o `nginx:alpine` ofrecen un balance óptimo entre funcionalidad y tamaño.

**Acción**: Identifica la imagen base necesaria para tu tecnología (Node.js, Python, Java, Go, etc.) y verifica su versión en el registro de Docker Hub.

### Paso 2: Configurar el entorno de ejecución
Crea un Dockerfile que defina la estructura de la imagen. Incluye:
- Etiquetas de versión (COPY, RUN, CMD).
- Instrucciones de instalación de dependencias.
- Configuración de variables de entorno.
- Optimización de capas para reducir tamaño.

**Acción**: Escribe un Dockerfile para un servicio de tu proyecto actual y ejecuta `docker build -t mi-servicio:latest .`.

### Paso 3: Desarrollar en contenedor
Desplaza el desarrollo desde el host al contenedor para garantizar consistencia. Usa `docker-compose` para definir redes, volúmenes y servicios dependientes (base de datos, caché, API).

**Acción**: Crea un archivo `docker-compose.yml` que orqueste tu aplicación y sus dependencias, luego ejecuta `docker-compose up -d`.

### Paso 4: Probar en producción-like
Simula el entorno de producción creando un contenedor con las mismas configuraciones de red, volúmenes y variables de entorno que tendrá en producción. Valida que la aplicación funcione correctamente bajo cargas simuladas.

**Acción**: Ejecuta pruebas de estrés con `hey` o `locust` dentro del contenedor y verifica métricas de latencia y throughput.

### Paso 5: Despliegue y escalado
Una vez validado, despliega el contenedor en un orquestador (Kubernetes, Docker Swarm) o en un cluster de servidores. Utiliza estrategias de despliegue gradual (blue-green, rolling update) para minimizar el impacto en el servicio.

**Acción**: Documenta el procedimiento de despliegue y establece alertas para monitorear salud del contenedor.

## 4. EJEMPLO REAL

**Caso: Plataforma de E-commerce en Medellín**

Una tienda online de accesorios masculinos en Medellín experimentaba problemas de inconsistencia entre desarrollo y producción. Los desarrolladores reportaban errores de dependencia de bibliotecas y tiempos de arranque lentos en producción. Tras implementar Docker:

1. **Imagen base**: Se creó una imagen `node:18-alpine` con Express.js y las dependencias de la API.
2. **Volumen de datos**: Se montó un volumen persistente para el catálogo de productos, evitando pérdida de datos al reiniciar el servicio.
3. **Red aislada**: Se configuró una red de microservicios que permitió escalar la API de pedidos independientemente del catálogo.
4. **Resultados**: Tiempo de arranque del contenedor reducido de 45 segundos (VM) a 8 segundos (Docker). La tasa de error en producción disminuyó de 4.2% a 0.8% tras la estandarización del entorno.

**Métricas antes/después**:
- Tiempo de arranque: 45s → 8s (5.6x reducción)
- Errores en producción: 4.2% → 0.8%
- Consistencia entre entornos: 92% → 99.5%

Este caso demuestra cómo Docker elimina la brecha entre "lo que funciona en mi laptop" y "lo que funciona en producción", reduciendo el tiempo de debugging en un 70% y mejorando la estabilidad del sistema.

## 5. RETO DEL DÍA

**Tarea (5-10 minutos)**: Configura un contenedor Docker para una aplicación existente en tu flujo de trabajo.

1. Identifica un servicio pequeño (por ejemplo, una API REST o un script de backend) que se ejecute actualmente en tu máquina.
2. Crea una imagen Docker minimalista basada en la tecnología del servicio (Node.js, Python, Go, etc.).
3. Construye la imagen con `docker build -t mi-servicio:dev .`.
4. Ejecuta el contenedor en modo detach (`docker run -d -p 8080:8080 mi-servicio:dev`).
5. Verifica que la aplicación responda en el puerto 8080 y registra la salida en tu terminal.

**Criterio de éxito**: El contenedor arranca en menos de 30 segundos y responde a solicitudes HTTP con código 200 OK. Si el contenedor no arranca, revisa la imagen (error en build) o las dependencias faltantes.

Este ejercicio te permite practicar el ciclo completo de Docker: construcción, ejecución y validación. La habilidad de replicar un entorno de desarrollo en producción es fundamental para cualquier desarrollador moderno.
