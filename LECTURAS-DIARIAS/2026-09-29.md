# Concurrencia vs Paralelismo — Diferencia real y cuándo usar cada uno

**Fecha:** 2026-09-29
**Categoría:** I — Ingeniería y Diseño
**Ley:** Concurrencia vs Paralelismo

---

## 1. QUÉ ES

**Concurrencia** es la capacidad de un sistema de *manejar múltiples tareas a la vez* (intercalándolas) aunque el hardware solo ejecute una a la vez. Es un concepto de *estructura*: el programa está diseñado para que varias tareas progresen sin bloquearse entre sí.

**Paralelismo** es la ejecución *simultánea real* de varias tareas, usando múltiples núcleos de CPU o múltiples máquinas. Es un concepto de *ejecución*: dos o más instrucciones corren literalmente al mismo instante.

Diferencia clave en una línea:
- **Concurrencia = lidiar con muchas cosas a la vez** (intercalado, lógica).
- **Paralelismo = hacer muchas cosas a la vez** (simultáneo, hardware).

No son lo mismo ni son intercambiables. Un programa puede ser concurrente sin ser paralelo (un solo núcleo que alterna tareas), y puede ser paralelo sin ser concurrente (tareas independientes que no comparten estado). La confusión entre ambos es la causa #1 de bugs de carrera y de diseños que no escalan.

---

## 2. CÓMO FUNCIONA

### El mecanismo de la concurrencia
El sistema operativo (o el runtime, como Node.js o Go) usa un **scheduler** que divide el tiempo de CPU en rebanadas (time slices, típicamente 1–10 ms) y las reparte entre tareas. Cada tarea "avanza un poco" y cede el turno. Para el usuario se siente simultáneo; para la CPU es intercalado.

Ejemplo concreto: Node.js es **concurrente pero de un solo hilo**. Cuando haces una petición HTTP, Node lanza la petición, *no espera* (no bloquea), y sigue atendiendo otras. Cuando la respuesta llega, retoma donde quedó. En un solo núcleo, atiende miles de conexiones "a la vez" aunque físicamente ejecute una por vez. Por eso Node maneja bien I/O (red, disco, bases de datos) — esas esperas no consumen CPU.

### El mecanismo del paralelismo
El paralelismo requiere **múltiples unidades de ejecución**: hilos (threads), procesos, o máquinas. Un CPU moderno de 8 núcleos puede ejecutar 8 instrucciones en el mismo instante. Para aprovecharlo necesitas dividir el trabajo en partes independientes.

Ejemplo concreto: procesar 1 millón de imágenes. En un solo hilo tardas 100 segundos. Con 8 hilos en 8 núcleos, si la tarea es independiente (cada imagen no depende de otra), tardas ~12.5 segundos (ideal). Eso es paralelismo: misma tarea, fragmentada, ejecutada simultáneamente.

### Por qué se confunden
- **Ambos aceleran** (apariencia de velocidad).
- **Ambos usan "hilos" o "tareas"** en la jerga.
- **Muchos problemas son ambos a la vez**: un servidor web es concurrente (maneja muchas conexiones intercaladas) y paralelo (usa varios núcleos).

### El costo oculto: el estado compartido
El paralelismo real introduce el problema que la concurrencia no tiene: **condiciones de carrera (race conditions)**. Si dos hilos leen y escriben la misma variable sin protección, el resultado depende del orden exacto de ejecución — impredecible. Por eso necesitas locks, mutexes, o estructuras inmutables. El paralelismo solo vale la pena si el costo de sincronización no supera la ganancia.

**Regla empírica (ley de Amdahl):** la aceleración máxima está limitada por la parte *secuencial* del programa. Si el 25% de tu trabajo no se puede paralelizar, la aceleración máxima es ~4x sin importar cuántos núcleos uses (1 / (0.25 + 0.75/N), con N→∞ da 1/0.25 = 4). Más núcleos no siempre significa más velocidad.

## 3. APLICACIÓN PRÁCTICA

### Paso 1: Diagnostica qué tipo de trabajo tienes
- ¿Es **I/O-bound** (esperas de red, disco, API, base de datos)? → Concurrencia (async/eventos) es suficiente y barata.
- ¿Es **CPU-bound** (cálculo, procesamiento de datos, renderizado)? → Necesitas paralelismo real (múltiples núcleos).
- ¿Es **mixto**? → Combina ambos: concurrencia para el I/O, paralelismo para el cómputo.

### Paso 2: Mide antes de optimizar
No asumas. Mide con un perfilador o un cronómetro simple:
```bash
time your_command
```
Compara: versión secuencial vs versión concurrente vs versión paralela. Si la ganancia es < 20%, no vale la pena el costo de complejidad.

### Paso 3: Elige la herramienta según el caso
| Tipo de trabajo | Herramienta | Ejemplo |
|---|---|---|
| I/O-bound | Async/eventos (Node, asyncio, Go) | Servidor web, scraping, llamadas API |
| CPU-bound, mismo proceso | Threads / multiprocessing | Procesar imágenes, cálculos |
| CPU-bound, escala grande | Múltiples procesos / colas de mensajes | Pipeline de datos, workers |
| Muy grande | Múltiples máquinas (cluster) | Entrenar modelos, ETL masivo |

### Paso 4: Protege el estado compartido
Si usas paralelismo real:
- Prefiere **estructuras inmutables** (no compartas variables mutables).
- Si debes compartir, usa locks o colas thread-safe.
- Divide el trabajo en **tareas independientes** (sin dependencias entre sí) para evitar sincronización.

### Paso 5: Escala en capas
Empieza concurrente (más simple), y solo añade paralelismo cuando el cuello de botella sea real y medible. La regla: **primero hazlo correcto, luego rápido, y solo paraleliza el 20% que importa** (regla 80/20).

## 4. EJEMPLO REAL

**Caso: API de scraping de precios para un e-commerce de comparación.**

**Antes (secuencial):** Un script que consultaba 100 sitios de proveedores uno tras otro. Cada petición tardaba ~2 segundos (I/O-bound, esperando la red). Total: 100 × 2s = **200 segundos (~3.3 min)** para actualizar el catálogo. El script corría una vez por hora, y el dato de precios estaba desactualizado la mayor parte del tiempo.

**Después (concurrente):** Se reescribió con async (Node.js). Las 100 peticiones se lanzan "a la vez" y se espera la respuesta de todas. Como el tiempo de espera de red no consume CPU, el total bajó a ~**3 segundos** (el tiempo de la petición más lenta, no la suma). Mismo hardware, un solo hilo.

**Datos:**
- Antes: 200 s por ciclo, 18 ciclos/día (1 vez/hora) = ~3600 s/día de CPU ocupada.
- Después: 3 s por ciclo, 24 ciclos/día (cada hora) = ~72 s/día.
- **Reducción: 98% del tiempo de cómputo**, y el catálogo ahora se actualiza cada hora en vez de cada 3 horas.

**Lección:** Este problema era I/O-bound. Añadir paralelismo (múltiples núcleos) NO habría ayudado — el cuello de botella era la espera de red, no la CPU. La concurrencia (async) resolvió el 98% del problema con la mínima complejidad. El paralelismo solo se necesitaría si, además, hubiera que procesar los datos con CPU pesado (por ejemplo, parsear y deduplicar 1M de precios) — ahí sí se usarían múltiples núcleos.

## 5. RETO DEL DÍA (5–10 min)

Elige una tarea que hagas hoy y que espere algo (una descarga, una API, un script que procesa archivos). Mídela con `time` o un cronómetro.

1. **Mide el tiempo actual:** corre la tarea y anota los segundos.
2. **Identifica el tipo:** ¿espera de red/disco (I/O) o cálculo pesado (CPU)?
3. **Aplica la corrección mínima:**
   - Si es I/O → busca o escribe una versión async/concurrente (en Python: `asyncio` o `ThreadPoolExecutor` con 10 threads; en Node: `Promise.all`).
   - Si es CPU → usa `multiprocessing` (Python) o divide el trabajo en 4–8 procesos (tantos como núcleos: `nproc`).
4. **Mide de nuevo** y calcula la aceleración (tiempo_antes / tiempo_después).

**Meta:** lograr al menos 3x de aceleración con menos de 15 líneas de cambio. Si no la logras, documenta por qué (probablemente era secuencial por dependencia o ya era rápido) — eso también es un dato válido.

**Checklist final:**
- [ ] Medí antes y después
- [ ] Identifiqué I/O vs CPU
- [ ] Apliqué concurrencia o paralelismo (no ambos al azar)
- [ ] Anoté la aceleración y la causa
